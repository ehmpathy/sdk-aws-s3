# 3.1.1 external research — vision-flagged topics

> vision: `1.vision.yield.md`. two topics carry a `[research]` tag:
> 1. **del-absent behavior** — does `del` + `condition: { etag }` on an absent object return 412 or 204/404?
> 2. **409 model shape** — how does http 409 `ConditionalRequestConflict` differ from 412, and what is the correct response?

both topics center on the exact http semantics of s3 conditional writes/deletes. the research
confirms the empirical finding already baked into the build, and pins the 409-vs-412 distinction.

> note: several quotes below are cloned verbatim from aws documentation and reproduce aws's own
> wording (including the term "existing"); they are unaltered citations, not our prose.

---

## topic 1 — del + condition.etag on an ABSENT object

### verdict: **404 Not Found** (not 412, not 204)

The vision flagged this as unverified ("aws docs are silent for plain `IfMatch`"). the current aws
documentation is no longer silent — it now states the absent case explicitly.

**[FACT]** a conditional delete (`If-Match` with an ETag) against an object that does not exist
returns a **404 Not Found**.

> "If the object doesn't exist when evaluating either of the preconditions, S3 rejects the request
> and returns a `Not Found` error response." — [1] (official, conditional-deletes userguide)

> "You will receive a `404 Not Found` response if a concurrent delete request to an object succeeds
> before a conditional write operation on that object completes, as the object key no longer
> exists." — [1] (official)

**[FACT]** a conditional delete where the object IS present but the ETag does NOT match returns
**412 Precondition Failed** (distinct from the absent case):

> "If there's an existing object with the same key name and matching `ETag`, the `DeleteObject`
> requests succeeds, and returns a `204 No content` response. If the `ETag` doesn't match, the
> delete operation fails with a `412 Precondition Failed` response." — [1] (official)

**[FACT]** the `If-Match: *` (exists-check) variant returns **204 No Content** on success, and 412
only when the current version is a delete marker:

> "when you use `If-Match:*` with a `DeleteObject` API, the operation will only succeed with a
> `204 No Content` if the object exists. If the latest version of the object is a delete marker,
> the object doesn't exist and the `DeleteObject` API will fail and return a `412 Precondition
> Failed` response." — [1] (official)

### contract implication (convergence with the build)

three response codes now converge on one meaning for a caller's fenced write: "my conditional
operation did not land."

| caller intent | object state | s3 code |
|---------------|--------------|---------|
| compare-and-delete (`If-Match: etag`) | present, etag matches | 204 (success) |
| compare-and-delete (`If-Match: etag`) | present, etag differs | 412 |
| compare-and-delete (`If-Match: etag`) | **absent** | **404** |

**[FACT]** this exactly matches the empirical finding recorded in the 5.1 execution yield and
proven by the repo's integration test: a conditional `del` of an absent object returns
`NoSuchKey`/404, and the build maps 404-on-a-conditional-op → the same typed
`S3PreconditionFailedError` so consumers catch a single "my fenced write did not happen" error.
the external docs [1] now ratify that empirical result — the `[research]` flag is resolved.

**[SUMP]** an assumption worth stating: aws's conditional-**delete** feature for general-purpose
buckets was announced **Sep 16, 2025** [5], *after* the conditional-**write** feature
(Aug 2024 [4]). so the "docs are silent" note in the vision reflected a real gap at authoring
time that aws later filled — the behavior was always 404, but only recently documented.

## topic 2 — 409 ConditionalRequestConflict vs 412 PreconditionFailed

### verdict: **412 = precondition verdict (stop); 409 = concurrency conflict (retry)**

**[FACT]** 412 is a *decided* verdict — the precondition was evaluated and did not hold:

> "If there's an existing object, the write operation fails, resulting in a `412 Precondition
> Failed` response." — [2] (official, conditional-writes userguide)

> "If multiple conditional writes or copies occur for the same object name, the first write
> operation to finish succeeds. Amazon S3 then fails subsequent writes with a `412 Precondition
> Failed` response." — [2] (official)

**[FACT]** 409 is a *concurrency* signal — a conflicting in-flight operation, and the correct
response is to **retry** (not to treat it as a lost race):

> "You can also receive a `409 Conflict` response in the case of concurrent requests if a delete
> request to an object succeeds before a conditional write operation on that object completes.
> When using conditional writes with `PutObject`, uploads may be retried after receiving a
> `409 Conflict` error." — [2] (official)

**[FACT]** the header used changes which code a concurrent delete produces — `If-None-Match` yields
409, `If-Match` yields 404:

> "This scenario will result in a `409 Conflict` response for an `If-None-Match` header and a
> `404 Not Found` response for an `If-Match` header." — [2] (official)

**[FACT]** on an `If-Match` write, a 404 (object deleted mid-flight) also warrants a re-upload:

> "You will receive a `404 Not Found` response if a concurrent delete request to an object succeeds
> before a conditional write operation on that object completes... You should reupload the object
> when you receive a `404 Not Found` response." — [2] (official)

**[FACT]** convergence — an independent practitioner source states the same retry guidance:

> "On a 409 failure, retry the upload. When using If-Match, you should fetch the object's ETag and
> retry the upload." — [3] (practitioner summary, aggregating aws guidance)

### contract implication

**[KHUE]** the vision's open question — "should 409 be its own typed `S3ConditionalConflictError`,
or a documented retry contract?" — remains a design (architect-stone) decision. the research
firms the *requirement* (409 must be modeled distinctly from 412 because the correct responses
diverge: stop vs retry) but not the *shape*. the build's current posture (409 → an internal-only
`S3ConditionalConflictError extends MalfunctionError`, mapped but not publicly exported pending the
architect stone) is consistent with this: 409 is not propagated raw, and its public shape is
deferred.

**[OPIN]** for a mutex/lock use case, treating 412 as "expected — someone else holds the lock"
and 409 as "transient — retry" is the ergonomic split most sources implicitly endorse; a consumer
should not blanket-retry a 412 (the lock is genuinely held) but should retry a 409 (a race that
may resolve).

## conflict detection

- **no direct conflicts** among the sources on the core facts. all official pages [1][2] and the
  practitioner sources [3][4] agree: 412 = precondition not met, 409 = concurrency conflict
  (retry), and the header choice (`If-Match` vs `If-None-Match`) determines whether a concurrent
  delete surfaces as 404 or 409.
- **apparent (not real) tension**: search snippets summarizing [1] variously said "404" for a
  conditional delete of a non-existent object, while the `If-Match: *` path returns "204 on
  success / 412 on delete-marker". these are different preconditions, not a contradiction — the
  full page [1] disambiguates: plain `If-Match: etag` on an absent object → 404; `If-Match: *` on
  a delete-marker → 412; `If-Match: *` on a present object → 204.

## convergence signal

- **3+ independent sources agree** that s3 conditional writes deliver put-if-absent and
  compare-and-swap semantics with 412 on precondition failure: official [2], InfoQ [4], and the
  4sysops/Medium practitioner writeups [6][7].
- **2 official pages + 1 practitioner** [1][2][3] agree on the 409-retry / 412-stop split.
