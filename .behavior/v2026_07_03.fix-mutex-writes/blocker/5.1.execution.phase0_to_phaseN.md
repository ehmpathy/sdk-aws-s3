## B. `function` overloads on get.one / set (vs rule.require.arrow-only)

**decision: KEEP the `function` keyword.**

the return-narrow overloads let `include.meta` narrow the return type
(`get.one({ ... })` → `string | null`; `get.one({ ..., include:{ meta:true } })` →
`{ body; meta } | null`). this is PROVEN unsatisfiable as an arrow:

```
src/domain.operations/getOne.ts(32,14): error TS2322:
  Type '(input) => Promise<string | { body; meta } | null>' is not assignable to type 'GetOne'.
  Type '{ body; meta }' is not assignable to type 'string'.
```

the arrow + callable-interface form can not express return-narrow overloads — the wide impl
return is not assignable to the narrow overload sig. the only two escapes are the `function`
keyword or an `as`-cast. `rule.forbid.as-cast` forbids the cast. so `rule.require.arrow-only`
and `rule.forbid.as-cast` directly conflict here; the `function` keyword is the type-safe
resolution (it avoids a cast that would blind the type system). documented inline in
getOne.ts / set.ts.

## C. get/set/del names (vs rule.require.get-set-gen-verbs / forbid.nonidempotent-mutations)

**decision: KEEP get/set/del.**

get/set/del is the deliberate, already-published (v0.1.1) public sdk triad. it mirrors the
universal object-store mental model (s3, localStorage, redis). `set` is idempotent (PutObject
overwrites), so the safety intent of forbid.nonidempotent-mutations holds. this is an
sdk-boundary ergonomic exception — analogous to how rule.prefer.optional-input-for-sdk-ux
overrides forbid.undefined-inputs at the same boundary. a rename to upsert/delete would be a
semver-major public-api change with no ergonomic gain.
