# 1.vision — conditional writes for sdkAwsS3

> wish: fulfill [ehmpathy/sdk-aws-s3#5](https://github.com/ehmpathy/sdk-aws-s3/issues/5)
> add conditional-write support (put-if-absent, compare-and-set) + surface etag

---

## the outcome world

### day-in-the-life

a consumer builds a distributed lock over a shared external account. today they write a
sentinel file, wait, then re-read to see who won the election — a best-effort dance that
leans on s3 strong consistency. it works, but it's a settle-then-verify workaround, not a
true atomic primitive.

with conditional writes, they write once with `condition: { etag: null }` (assert absent). either
the object is created (they hold the lock) or a typed `S3PreconditionFailedError` is
thrown (someone else holds it). no wait. no re-read. one atomic call.

### before / after

```ts
// ❌ before — best-effort election (settle then verify)
await sdkAwsS3.set({ bucket, key: lockKey, body: myId });
await sleep(2000);                                  // settle
const holder = await sdkAwsS3.get.one({ bucket, key: lockKey });
const iWon = holder === myId;                       // hope nobody clobbered between

// ✅ after — atomic put-if-absent
try {
  const { meta } = await sdkAwsS3.set({
    bucket, key: lockKey, body: myId,
    condition: { etag: null },                      // expect absent → create only if absent
    include: { meta: true },                        // opt in to get the fence token back
  });
  // i hold the lock; meta.etag is my fence token
} catch (error) {
  if (error instanceof S3PreconditionFailedError) {
    // someone else holds the lock
  } else throw error;
}
```

### the "aha" moment

the value clicks when a consumer releases a lock safely:

```ts
// release ONLY our version — never clobber a lock we no longer hold
await sdkAwsS3.del({ bucket, key: lockKey, condition: { etag: myEtag } });
```

the etag returned at acquire-time becomes a **fence token**. compare-and-delete guarantees
we never delete a lock that expired and got re-acquired by someone else. that's the leap
from "best-effort" to "fenced" — the whole point of the wish.

## user experience

### usecases & goals

| usecase | goal | primitive |
| --- | --- | --- |
| distributed lock | acquire only if unheld (+ get fence token) | `set` + `condition: { etag: null }` + `include: { meta: true }` |
| lock release | release only our own hold | `del` + `condition: { etag: <etag> }` |
| optimistic concurrency | write only if unchanged since read | `set` + `condition: { etag: <etag> }` |
| read-modify-write | detect concurrent edit | `get.one` + `include: { meta: true }` → `set` `condition: { etag }` |

### contract inputs & outputs

the `condition` carries a single `etag` field that asserts the *expected current state* of the
object. this maps 1:1 onto the only two write-conditions s3 offers — see the map table below.

```ts
// set — backwards-compat by default; opt-in meta envelope via type overload (mirrors get.one)
//
// default — returns void (non-break); input field `body` (matches aws Body — see below)
sdkAwsS3.set(
  input: S3Ref<'object'> & {
    body: string;
    condition?: { etag: string | null };
  },
  context?: ContextSdkAwsS3,
): Promise<void>;

// opt-in — request meta → { meta: { etag } } (the etag of the written object)
sdkAwsS3.set(
  input: S3Ref<'object'> & {
    body: string;
    condition?: { etag: string | null };
    include: { meta: true };
  },
  context?: ContextSdkAwsS3,
): Promise<{ meta: { etag: string } }>;

// del — condition optional; etag string only (s3 has no delete-if-absent)
sdkAwsS3.del(
  input: S3Ref<'object'> & {
    condition?: { etag: string };
  },
  context?: ContextSdkAwsS3,
): Promise<void>;

// get.one — backwards-compat by default; opt-in meta envelope via type overload
//
// default — UNCHANGED, returns the body string (non-break)
sdkAwsS3.get.one(
  input: S3Ref<'object'>,
  context?: ContextSdkAwsS3,
): Promise<string | null>;

// opt-in — request meta → richer { body, meta } envelope
sdkAwsS3.get.one(
  input: S3Ref<'object'> & { include: { meta: true } },
  context?: ContextSdkAwsS3,
): Promise<{ body: string; meta: { etag: string } } | null>;
```

both `get.one` and `set` use the **same opt-in `include?: { meta: true }` pattern**. `include` is
**optional** — omit it and you get today's default shape (that is what preserves backwards-compat).
output shape keys off the input via **type overload**:

- `get.one`: `include` omitted → `string | null` (today's contract, untouched); `include: { meta: true }`
  → `{ body, meta: { etag } } | null`.
- `set`: `include` omitted → `void` (today's contract, untouched); `include: { meta: true }` →
  `{ meta: { etag } }`.

every extant caller that omits `include` stays byte-for-byte compatible; only callers who ask for
meta pay the destructure tax. `meta` is a shared envelope so future fields (`contentLength`,
`lastModified`, `versionId`) slot in with no further break.

**one word for the object bytes: `body`, everywhere** (`set` input, `get.one` output, `getAll`
output). per `rule.require.ubiqlang` we pick a single canonical term — `body` and `content` for the
same concept is synonym drift. `body` is the aws/s3 domain word: the SDK exposes the object bytes as
`Body` on `PutObjectCommand` and `GetObjectOutput` (the http message body). in http/aws the
`Content-*` family names the *metadata that describes* the payload (`Content-Type`, `Content-Length`),
not the payload itself — so `body` is the honest noun for the bytes, and it keeps us consistent with
the ecosystem consumers already know. ⚠️ this renames `getAll`'s extant output `content → body` — the
**one break** in the set (see triage). we take it now, pre-1.0, while we already revise these ops.

**how `condition.etag` maps to s3 preconditions:**

| `condition` | asserts | s3 header | operation |
| --- | --- | --- | --- |
| omitted | don't care | (none) | unconditional — last-writer-wins |
| `{ etag: null }` | object absent | `IfNoneMatch: '*'` | put-if-absent (set only) |
| `{ etag: '"abc"' }` | object is this version | `IfMatch: '"abc"'` | compare-and-set / compare-and-delete |

why a single field, not two (`ifNoneMatch` + `ifMatch`): s3 accepts only `IfNoneMatch: '*'` on a
write — there is no "if-none-match a *specific* etag" (verified `models_0.d.ts:14717`: "Expects
the '*' character"). so the entire write-condition space is exactly {absent, matches-etag-X},
which `string | null` models precisely — with no representable conflict and no stray `'*'` literal.

on precondition failure (http 412), throw a typed **`ConstraintError`** subclass (caller-must-fix,
exit code 2):

```ts
// class S3PreconditionFailedError extends ConstraintError
throw new S3PreconditionFailedError({ ref, condition });
```

conditional writes have a **second** failure code: a concurrent in-flight collision returns
http **409 `ConditionalRequestConflict`** (verified: `models_0.d.ts:14703-14705`, `14715-14716`).
409 is not a "precondition not met" verdict — aws guidance is to re-read the etag and retry.
since a mutex operates under contention, 409 is a real path, not a footnote. how we model it
(distinct `S3ConditionalConflictError` vs a documented retry contract) is an architect-stone
decision — see open questions.

### timeline of a lock lifecycle

```
t0  acquire:  set({ ..., condition: { etag: null }, include: { meta: true } }) → { meta: { etag: 'abc' } }   // won
t1  work:     ...do the serialized work...
t2  release:  del({ ..., condition: { etag: 'abc' } })                                                        // safe
```

a loser's timeline:

```
t0  acquire:  set({ ..., condition: { etag: null }, include: { meta: true } }) → throws S3PreconditionFailedError
t1  backoff:  retry later, or give up
```

### read-modify-write (opt-in meta)

```ts
// read WITH meta → get the current etag to fence the write-back
const found = await sdkAwsS3.get.one({ bucket, key, include: { meta: true } });
if (!found) return;

const next = transform(found.body);

// write back ONLY if unchanged since our read
await sdkAwsS3.set({ bucket, key, body: next, condition: { etag: found.meta.etag } });
// throws S3PreconditionFailedError if someone else wrote between our read and write
```

the plain read stays plain — a caller who omits `include` still gets `string | null`:

```ts
const body = await sdkAwsS3.get.one({ bucket, key }); // string | null, unchanged
```

## mental model

### how a user describes it to a friend

> "s3 now has `create-only-if-absent` and `overwrite-only-if-unchanged`, like a
> compare-and-swap for files. the sdk hands you an etag as a receipt, and you can say
> 'only delete if the receipt still matches' — so you never stomp on someone else's write."

### analogies

- **fence token**: the etag is a numbered ticket; the door only opens if your ticket is current.
- **compare-and-swap (CAS)**: `condition: { etag }` is CAS for objects — the atomic primitive locks are built on.
- **optimistic lock**: like a `version` column with `WHERE version = ?` on update.

### their terms vs our terms

| user says | we say |
| --- | --- |
| "create if not there" | `condition: { etag: null }` |
| "only if unchanged" | `condition: { etag: <etag> }` |
| "receipt" / "version" | `etag` |
| "it was already locked" | `S3PreconditionFailedError` (a `ConstraintError`, http 412) |

## evaluation

### how well it solves the goals

- ✅ **put-if-absent**: `PutObjectCommand` with `IfNoneMatch: '*'` — verified supported by
  `@aws-sdk/client-s3@3.1042.0` (`PutObjectRequest.IfNoneMatch`).
- ✅ **compare-and-set**: `PutObjectCommand` with `IfMatch: <etag>` (`PutObjectRequest.IfMatch`).
- ✅ **compare-and-delete**: `DeleteObjectCommand` with `IfMatch: <etag>` (`DeleteObjectRequest.IfMatch`).
- ✅ **etag surfaced**: `GetObjectOutput.ETag` and `PutObjectOutput.ETag` both present.

fully covers the wish's acceptance criteria.

### pros

- true atomic locks (fenced), not best-effort — the core ask.
- `condition` is optional → zero friction for the common get/set/del case (honors
  `rule.prefer.optional-input-for-sdk-ux`).
- **single `etag` field makes conflicts unrepresentable** — one field can't clash with itself, so
  there's no "both conditions supplied" error to guard, and no stray `'*'` literal to explain.
  the type *is* the pit of success.
- **both `get.one` and `set` stay fully backwards-compat** — meta is opt-in via the *same*
  `include: { meta: true }` overload on both ops; defaults (`string | null`, `void`) are untouched.
  no coordinated consumer update needed.
- **symmetric read/write meta** — one `include` pattern, one `meta` envelope, on both ops. a
  consumer learns it once and applies it everywhere.
- typed error keeps consumers in a pit of success — `instanceof S3PreconditionFailedError`
  beats string-matching on http 412.

### cons

- **input-dependent output shapes on two ops** — `get.one` (`string | null` vs `{ body; meta }`)
  and `set` (`void` vs `{ meta }`) each return one of two shapes based on `include`. type overloads
  carry this cleanly, but it is more surface than flat returns. the tradeoff buys full
  backwards-compat + symmetry, which is worth it.
- etag semantics: s3 etags are only an md5 for simple (non-multipart, unencrypted) puts.
  as an opaque fence token this is fine — we never interpret it, just echo it back.

### edgecases & pit-of-success

| edgecase | contract behavior |
| --- | --- |
| conflicting conditions | **unrepresentable** — a single `etag` field cannot conflict with itself; the old two-field `ifNoneMatch`+`ifMatch` clash simply cannot occur |
| `condition: { etag }` on `del` when object absent | ⚠️ **unverified** — aws docs do not state the absent case for plain `IfMatch` delete; s3 delete is normally idempotent (204). must confirm empirically in a build stone before we promise 412 |
| `condition` omitted | plain last-writer-wins (today's behavior, unchanged) |
| 412 precondition failure | typed `S3PreconditionFailedError` (a `ConstraintError`, exit 2) — decided outcome, do not retry blindly |
| 409 concurrent conflict | separate signal; correct response is re-read etag + retry (per aws) — must be modeled, not propagated raw |
| other 4xx / 5xx | propagate raw `S3ServiceException` |
| `del` + `condition: { etag: null }` | **unrepresentable** — `del` condition is typed `{ etag: string }`; s3 has no delete-if-absent, so the type forbids it |

## open questions & assumptions

### assumptions

1. **backwards-compat by default — one deliberate break.** the meta envelope is opt-in via type
   overload on `get.one` and `set`, so their defaults (`string | null`, `void`) are preserved and
   `svc-notifications`' reads are untouched. the **one** intentional break is the ubiqlang rename of
   `getAll`'s output `content → body` (see triage) — taken now, pre-1.0, to unify the object-bytes
   term on aws's `body`. we do not spend any break we don't have to; this one buys a single canonical
   vocabulary aligned with the s3 SDK.
2. **opaque etag is sufficient** as a fence token — consumers never parse it.
3. **`getAll` etag is out of scope** for this wish (it returns `{ key, body }[]`; the wish
   names only `get.one` / `set`). flag but don't expand scope.
4. **throw on precondition failure** — the wish states "throw a typed error." honored, but for a
   lock, "already held" is an *expected* outcome, not an exceptional one (see q5).

### open questions — triaged

each question is tagged **[answered]** (resolved now via logic / code), **[research]** (to be
answered in a later research or build stone), or **[wisher]** (only the wisher can decide).

#### [answered] — resolved now

- **q1 — etag surface on `get.one` AND `set`.** resolved with the wisher: **backwards-compat by
  default**, meta opt-in via the *same* **type overload** `include?: { meta: true }` on both ops.
  `include` omitted → today's shape (`get.one` → `string | null`, `set` → `void`, both untouched);
  `include: { meta: true }` → `get.one` `{ body, meta: { etag } } | null`, `set` `{ meta: { etag } }`.
  no break — `svc-notifications` and every extant caller that omits `include` stay compatible. `meta`
  is a shared envelope for future fields; one `include` pattern makes read/write symmetric.
- **q2 — `del` return shape.** keep `del` as `Promise<void>`. logic: a delete has no useful
  result to surface, the wish returns no value, and `del` stays idempotent. no reason to return
  an etag. (wisher may override, but the default is settled.)
- **q3 — error class.** resolved with the wisher: `S3PreconditionFailedError` is a **`ConstraintError`**
  (precondition-failed is caller-must-fix — exit code 2), introduced as a **custom subclass extension**
  (`class S3PreconditionFailedError extends ConstraintError`). this adds an error-lib dependency
  (`test-fns` / `helpful-errors` supply `ConstraintError` with the exit code built in) — a deliberate
  choice over the repo's current plain-`Error` posture, to fit ehmpathy fail-loud conventions.
- **q4 — `getAll` etag.** out of scope. the wish names only `get.one` / `set` for etag; to add
  `getAll` etag would be scope creep. exclude for this behavior.
- **q5 — throw vs return on contention.** resolved with the wisher: **throw-only**. a precondition
  failure throws `S3PreconditionFailedError`; there is no non-throw / `tryLock` variant in this
  behavior. keeps the surface minimal; consumers wrap acquire in try/catch. (a non-throw ergonomic
  path may be revisited later, but is out of scope now.)
- **object-bytes term: `body` everywhere.** resolved with the wisher: one canonical word for the
  object bytes — `set` input, `get.one` output, `getAll` output all use `body` per
  `rule.require.ubiqlang`. ⚠️ this **renames `getAll`'s extant output `content → body`**, the single
  break in the set. justified: `body` is the aws/s3 domain word (the SDK exposes the bytes as `Body`
  on `PutObjectCommand` / `GetObjectOutput`; `Content-*` in http/aws names the payload's *metadata*,
  not the payload), `set` already uses `body`, and pre-1.0 while we already revise these ops is the
  clean moment. the build stone must call this out in release notes / migration.
- **condition shape (`{ etag: string | null }`, not `{ ifNoneMatch; ifMatch }`).** resolved with
  the wisher: a single `etag` field asserts the expected current state — `null` = absent
  (`IfNoneMatch: '*'`), `string` = this version (`IfMatch`). this is not lossy: s3 accepts only
  `IfNoneMatch: '*'` on a write (`models_0.d.ts:14717`), so {absent, matches-etag-X} is the whole
  write-condition space. it makes conflicts unrepresentable and retires the earlier *proposed*
  "reject both conditions" guard (now moot — one field cannot conflict with itself).
- **condition placement (`input` not `options`).** resolved by `rule.require.input-options-pattern`:
  `condition` changes the *semantic intent* of the write (assert-absent vs assert-etag vs
  unconditional), like `body` — it is *what* the write is, not *how* it runs. it belongs in
  `input`, and honors `rule.prefer.optional-input-for-sdk-ux`.
- **etag round-trip fidelity (contract invariant).** s3 etags are http quoted-strings; s3
  returns them with the double-quotes intact (e.g. `"9a0364b9..."`), and the value passed to
  `condition.etag` reaches `If-Match` *verbatim*. the `etag` we surface must be the raw s3 value
  (quotes preserved), and the same value must pass back into `condition.etag` unchanged. do NOT
  strip / prettify the quotes — a tidied etag would silently fail every compare-and-set. "opaque"
  means "untouched", not just "unparsed". (an invariant, not a question — the build stone must honor it.)

#### [research] — answer in a later stone

- **del-absent behavior (build/integration stone).** does `del` + `condition: { etag }` on an
  *absent* object return `412` or an idempotent `204`? aws docs are silent for plain `IfMatch`;
  the directory-bucket `IfMatchSize` / `LastModifiedTime` variants say `204`. must be proven by
  integration test before the contract promises a behavior.
- **q6 — 409 model shape (architect stone).** `409 ConditionalRequestConflict` must be handled
  (aws says re-read etag + retry). whether it becomes its own typed error
  (`S3ConditionalConflictError`) or a documented retry contract is a design decision, informed by
  how consumers want to drive retries. the *need* to model 409 is settled; only its shape is open.

#### [deferred] — phase 2, out of scope for this behavior

- **read `fresh` escape hatch.** a future opt-in read modifier — e.g.
  `get.one(input, { fresh: true })` — to force a read past a memory-first cache to the source.
  presumes a cache layer this SDK does not have today (s3 reads are already strongly consistent),
  so it is **deferred to phase 2** and out of scope for the conditional-writes wish. recorded here
  so the read-side option surface stays coherent when a cache wrapper lands.

## what is awkward?

1. **`get.one` and `set` have input-dependent return types.** the `include` overload buys full
   backwards-compat, but each op's return shape now depends on whether `include: { meta: true }` is
   passed. type overloads express this cleanly, yet it is a little more machinery than a single flat
   return — a reader must know the overload exists to expect the envelope. worth it to avoid a break.
2. **`del` is the odd op out.** `get.one` and `set` share the `include`/`meta` opt-in; `del` has no
   meta (no useful result to return) and stays `void`. the read/write pair is symmetric, but `del`
   sits apart. defensible (a delete has no result), just not perfectly uniform across all three.
3. **`condition.etag: null` overloads `null`** — it reads as "no etag", but *means* "assert the
   object is absent", not "no condition". the "no condition" case is `condition` omitted entirely.
   this is a small semantic hop (null = the-absent-state, not the-absence-of-a-check), softened by
   the map table, but a reader could momentarily misread `{ etag: null }` as a no-op.
4. **`set` / `del` condition types differ** — `set` takes `{ etag: string | null }`, `del` takes
   `{ etag: string }`. the asymmetry is *truthful* (s3 has no delete-if-absent) and the type
   forbids the meaningless case, but the two ops no longer share one condition type.
5. **two distinct failure codes, not one.** 412 (precondition unmet) and 409 (concurrent
   conflict) mean different things and want different responses (stop vs retry). a mutex under
   contention will meet both. a model of only 412 would leave the retry path unhandled — so the
   error surface must be two-pronged, which is more than the wish's single typed error implied.
