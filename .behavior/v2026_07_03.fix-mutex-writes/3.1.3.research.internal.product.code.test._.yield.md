> researched against: wish `0.wish.md`, vision `1.vision.yield.md`, criteria `2.1` / `2.2`.
> scope: test codepaths only (production codepaths excluded). every claim cites file+line.

the repo has an established three-tier test taxonomy (unit / integration / acceptance) driven by
`test-fns` given/when/then. below, each relevant test pattern is enumerated with a
[REUSE] / [EXTEND] / [REPLACE] tag.

## pattern 2 — `useBeforeAll` scene + shared result [REUSE]

each `when` sets up a `scene` via `useBeforeAll`, then multiple `then` blocks assert against it —
avoids redundant expensive s3 calls.

**[cite 3]** `src/domain.operations/condition.integration.test.ts:20-30`
> ```ts
> const scene = useBeforeAll(async () => {
>   const written = await set({
>     bucket, key, body,
>     condition: { etag: null },
>     include: { meta: true },
>   });
>   const found = await getOne({ bucket, key });
>   return { written, found };
> });
> ```

relation to wish: every conditional-write case reuses the `scene`/`useBeforeAll` pattern to run
the s3 op once and assert body + meta + error across peer `then`s. **[REUSE]**.

## pattern 4 — unique keys via `getUuid()` for isolation [REUSE]

each case keys off a fresh uuid so parallel/repeat runs never collide.

**[cite 6]** `src/domain.operations/condition.integration.test.ts:17`
> ```ts
> const key = `test/${getUuid()}/put-if-absent-new.txt`;
> ```

relation to wish: every conditional case uses `getUuid()` in the KEY for run isolation.
**[REUSE]** — note this is a deliberate distinction from snapshot VALUES, which must stay
deterministic (see pattern 8).

## pattern 5 — `getError` + `toBeInstanceOf` for typed-error assertions [EXTEND — new in this repo]

conditional failures are captured via `getError` and asserted by type, not string.

**[cite 7]** `src/domain.operations/condition.integration.test.ts:49-59`
> ```ts
> const error = await getError(
>   set({ bucket, key, body: 'second', condition: { etag: null } }),
> );
> ...
> expect(scene.error).toBeInstanceOf(S3PreconditionFailedError);
> ```

relation to wish: pre-wish the repo had no typed domain errors, so no `getError`+`toBeInstanceOf`
error assertions existed. the wish **[EXTEND]s** the test vocabulary with `getError` (from
`helpful-errors`) and instance-of assertions. **[EXTEND]**.

## pattern 8 — deterministic unit test of the error-map, snapshot-safe [EXTEND — new]

the error-map transformer is unit-tested with a synthetic `S3ServiceException` and a **fixed** ref,
so snapshots carry no random uuid.

**[cite 10]** `src/domain.operations/throwMappedS3ConditionError.test.ts:9-10`
> ```ts
> // a fixed ref → deterministic error messages (safe to snapshot; no random uuids)
> const ref = { bucket: 'test-bucket', key: 'test/lock.txt' };
> ```

**[cite 11]** `src/domain.operations/throwMappedS3ConditionError.test.ts:13-21`
> ```ts
> const asS3Error = (input: { name: string; httpStatusCode: number }): S3ServiceException =>
>   new S3ServiceException({
>     name: input.name,
>     $fault: 'client',
>     $metadata: { httpStatusCode: input.httpStatusCode },
>   });
> ```

relation to wish: a net-new unit test that spies the error-map at the transformer grain (pure, no
i/o), with a fixed ref precisely so the message snapshot is stable. this establishes the
determinism discipline the acceptance snapshots must also follow. **[EXTEND]** — and it is the
in-repo precedent for the acceptance-snapshot determinism fix (fixed values, not random uuids).

---

## pattern 9 — message snapshot + behavioral assertion together [EXTEND]

error cases assert both the type (behavior) and the message (snapshot), never a snapshot alone.

**[cite 12]** `src/domain.operations/throwMappedS3ConditionError.test.ts:34-40`
> ```ts
> then('it throws a typed S3PreconditionFailedError', async () => {
>   expect(await error).toBeInstanceOf(S3PreconditionFailedError);
> });
> then('the message is actionable', async () => {
>   expect((await error).message).toMatchSnapshot();
> });
> ```

relation to wish: pairs a `toBeInstanceOf` behavioral check with a `toMatchSnapshot` on the
message — the snapshot never stands alone. **[EXTEND]** of the snapshot discipline (per
`rule.require.snapshots`: use both snapshots and explicit assertions).

---

## pattern 10 — collocated `.integration.test.ts` / `.acceptance.test.ts` [REUSE]

tests sit beside the code they exercise; acceptance at the contract, integration at the op grain.

**[cite 13]** file layout — `src/domain.operations/*.integration.test.ts` (op-grain) and
`src/contract/index.acceptance.test.ts` + `index.journey.acceptance.test.ts` (contract-grain),
per the vision's internal-research note (vision `1.vision.yield.md`, "test patterns").

relation to wish: the conditional-write tests follow the extant collocation + grain-to-scope
convention (transformers → unit, communicators/orchestrators → integration, contract →
acceptance). **[REUSE]**.

**test infra note:** the suites depend on `test-fns` (given/when/then, `useBeforeAll`),
`uuid-fns` (`getUuid`), `helpful-errors` (`getError`), and a real s3 bucket
(`ehmpathy-sdk-aws-s3-test-bucket`) reached via keyrack-provided aws creds. the acceptance runner
collects `**/*.acceptance.test.ts` (`jest.acceptance.config.ts`).

**⚠️ determinism caveat for [research]/[EXTEND] carry-forward:** pattern 4 (unique KEY) and the
snapshot-determinism discipline (pattern 8) must be held apart — the KEY may be a uuid for
isolation, but any value captured into a `toMatchSnapshot` must be a fixed literal or a masked
token, since the acceptance runner runs against real s3 in CI with no `--updateSnapshot`. this is
the pattern the verification-stone snapshot fix enforces repo-wide.
