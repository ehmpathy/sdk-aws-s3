# 3.3.1 product blueprint — conditional writes for sdkAwsS3

> wish: fulfill [ehmpathy/sdk-aws-s3#5](https://github.com/ehmpathy/sdk-aws-s3/issues/5)
> references: `2.1.criteria.blackbox.yield.md`, `2.2.criteria.blackbox.matrix.yield.md`,
> `3.1.1.research.external.product.flagged._.yield.md`,
> `3.1.3.research.internal.product.code.prod._.yield.md`,
> `3.1.3.research.internal.product.code.test._.yield.md`.

---

## summary

extend the extant `sdkAwsS3` wrapper (`get.one` / `get.all` / `set` / `del`) with s3 conditional
writes, so a consumer can:

- **put-if-absent** — `set({ ..., condition: { etag: null } })` → `IfNoneMatch: '*'`
- **compare-and-set** — `set({ ..., condition: { etag } })` → `IfMatch: etag`
- **compare-and-delete** — `del({ ..., condition: { etag } })` → `IfMatch: etag`
- **opt-in etag receipt** — `set(..., { include: { meta: true } })` and
  `get.one(..., { include: { meta: true } })` return `{ meta: { etag } }`
- **typed failure** — a precondition breach throws a single `S3PreconditionFailedError`
  (`instanceof`-catchable, actionable message), never a raw status string.

the shape of `sdkAwsS3` is untouched; only the member ops are enriched. backwards compat is held via
`function` overloads (omit `condition`/`include` → today's behavior byte-for-byte).

the one deliberate break: `get.all`'s output field `content` is renamed to `body`, to unify the
object-bytes term across all ops (per `rule.require.ubiqlang`).

**grain split rationale** (per `define.domain-operation-grains`): orchestrators (`set`/`getOne`/
`getAll`/`del`) read as narrative; communicators (`setS3Object`/`getS3Object`/`deleteS3Object`)
encapsulate raw i/o + error-map; transformers (`asS3Ref`/`asS3ConditionHeaders`/
`throwMappedS3ConditionError`) are pure. this keeps the orchestrators free of inline try/catch and
header-assembly decode-friction.

> **on communicator ↔ transformer composition (considered, retained)**: a communicator here calls
> two pure transformers — `asS3ConditionHeaders` (to build the precondition headers it sends) and
> `throwMappedS3ConditionError` (to translate the s3 error it catches). one interpretation holds that this
> makes the communicator a "micro-orchestrator" and the transformers should instead be called by the
> top-level orchestrator, with the communicator receiving pre-built headers and re-throwing raw. this
> blueprint retains the current shape deliberately: the header-build and error-map are intrinsic to
> the SINGLE i/o act (the conditional put/delete) — they are how this communicator speaks s3's
> conditional dialect, not a separate workflow. keeping them inside the communicator makes it a
> complete, self-contained i/o boundary that its own dedicated integration test can verify end-to-end
> (send-the-right-header, map-the-right-error), rather than splitting one atomic s3 interaction across
> two grains. the transformers remain pure and independently unit-tested, so reuse is preserved. this
> is a defended judgment call, surfaced here for reviewer scrutiny.

> **`ContextSdkAwsS3` placement — retained in `domain.objects/`**: `ContextSdkAwsS3` is a domain
> object (the injected-client context shape). its reference to `S3Client` is a TYPE-ONLY import —
> erased at compile time, so it carries no runtime infrastructure dependency and does not violate
> `rule.require.directional-deps`. a type annotation is not a structural (value) dependency: no value
> from `@aws-sdk/client-s3` is instantiated, imported as a value, or bundled. so it stays in
> `domain.objects/` alongside `S3Ref` and the typed errors, where the domain shapes belong.
>
> **`S3Ref` placement — retained in `domain.objects/`**: `S3Ref` is a pure structural type (a tagged
> `{ uri } | { bucket, key }` union) with no sdk import and no domain identity. it is shared across all
> four ops, so it lives in `domain.objects/` as a shared shape — the pre-wish `S3Ref` already lived
> there and imports naught from infra. this does NOT trip directional-deps (no upward/infra import).
>
> **`S3Ref` is a plain structural type, not branded/nominal**: `S3Ref<'object'>` / `S3Ref<'prefix'>`
> is a plain generic tagged union (`{ uri: string } | { bucket: string; key: string }`), structurally
> typed — any object of that shape satisfies it. this is deliberate for an SDK boundary (callers pass
> plain object literals with zero ceremony). the tradeoff, stated so it is a known choice: consumers
> cannot use `S3Ref` as a nominal discriminant in their own union types. the grain parameter
> (`'object'` vs `'prefix'`) narrows intent at the type level without requiring a runtime brand.

## contracts

| contract | shape | grain |
|----------|-------|-------|
| `set(input, context?)` | `include` lives in `input` (overload discriminant); `context?` is the 2nd arg → `void \| { meta: { etag } }` | orchestrator (contract) |
| `del(input, context?)` | `input: S3Ref<'object'> & { condition?: { etag: string } }` → `void` | orchestrator (contract) |

> **`del.condition.etag` non-nullable (by design)**: `set`'s condition is `{ etag: string \| null }`
> (null = put-if-absent), but `del`'s is `{ etag: string }` — non-nullable. this asymmetry is
> deliberate: there is no "delete-if-absent" semantics (deleting a thing that is not there is a no-op,
> not a precondition), so s3 offers no `IfNoneMatch` analogue for delete. the type forbids the
> meaningless row rather than accept-then-reject it.
>
> **`del` has no `include: { meta: true }` overload (by design)**: `set` and `getOne` each expose an
> `include: { meta: true }` overload to surface an etag; `del` does not. this is intentional, not an
> oversight: a delete removes the object, so there is no post-state etag to return — s3's delete
> response carries no useful entity-tag for the just-removed key. adding a `del` meta overload would
> imply a returnable etag that does not exist. stated here so a future contributor does not add it for
> false symmetry.
| `get.one(input, context?)` | `include` lives in `input` (overload discriminant); `context?` is the 2nd arg → `string \| { body: string; meta: { etag: string } } \| null` | orchestrator (contract) |
| `get.all(input, context?)` | `input: S3Ref<'prefix'>` → `{ key; body }[]` | orchestrator (contract) |

**exact overload signatures** (the `include` discriminant sits in `input`, NOT a separate `options`
arg — this is what lets the return type narrow at the call site without a cast, and matches the
vision's placement):

```ts
// set — default returns void (backwards-compat)
function set(
  input: S3Ref<'object'> & { body: string; condition?: { etag: string | null } },
  context?: ContextSdkAwsS3,
): Promise<void>;
// set — opt-in returns the written etag
function set(
  input: S3Ref<'object'> & { body: string; condition?: { etag: string | null }; include: { meta: true } },
  context?: ContextSdkAwsS3,
): Promise<{ meta: { etag: string } }>;

// getOne — default returns the body string (backwards-compat)
function getOne(
  input: S3Ref<'object'>,
  context?: ContextSdkAwsS3,
): Promise<string | null>;
// getOne — opt-in returns body + meta
function getOne(
  input: S3Ref<'object'> & { include: { meta: true } },
  context?: ContextSdkAwsS3,
): Promise<{ body: string; meta: { etag: string } } | null>;
```

> **`include` placement — `input`, not `options` (settles the vision/overload tension)**: earlier
> drafts described `include` as an `options?` arg. corrected here: `include` sits in the FIRST arg
> (`input`), because a TypeScript overload must discriminate on the argument the resolver inspects —
> an optional second `options` arg cannot select between a `void` and a `{ meta }` return without a
> runtime cast (which `rule.forbid.as-cast` bans). placing `include` in `input` matches the vision's
> own signature and is exactly what the shipped code does. the pure-config `(input, options)` idiom
> does not apply when the config value changes the return type; here it must be a typed discriminant
> in `input`.

typed errors + `S3Ref` are re-exported from `src/contract/index.ts` and `src/index.ts` so consumers
can `instanceof`-catch. `S3ConditionalConflictError` (409) IS currently publicly exported from both
barrels alongside `S3PreconditionFailedError`; what remains deferred to an architect stone is whether
to KEEP 409 public long-term (the `[KHUE]` open question) — not whether it is exported today. 409 is
never propagated raw; it is always mapped to the typed class.

both `S3PreconditionFailedError` and `S3ConditionalConflictError` carry a `@public` JSDoc tag on the
class declaration. because a consumer's `instanceof` check in their error handler becomes a silent
break if the type is ever renamed, the stability commitment is made explicit and searchable in the
public API surface rather than left implicit — a zero-cost, one-line-per-class signal.

**condition → header map** (the mechanism the vision requires):

| `condition` | s3 header | intent |
|-------------|-----------|--------|
| omitted | *(none)* | unconditional (last-writer-wins) |
| `{ etag: null }` | `IfNoneMatch: '*'` | put-if-absent |
| `{ etag: '<etag>' }` | `IfMatch: '<etag>'` | compare-and-set / compare-and-delete |

`asS3ConditionHeaders` return type is declared explicitly as
`{ IfNoneMatch?: string; IfMatch?: string }` — the omitted-condition row returns `{}` (an empty object
of that type), NOT `undefined`, so the result is always safe to spread into the s3 command input. the
return is exactly one of: `{}`, `{ IfNoneMatch: '*' }`, or `{ IfMatch: '<etag>' }`.

**s3 error → typed error map**:

| s3 status / name | typed error | who-fixes | research basis |
|------------------|-------------|-----------|----------------|
| 412 / PreconditionFailed | `S3PreconditionFailedError` (ConstraintError) | caller | `3.1.1...flagged._.yield.md` topic 2 [FACT], src [2] |
| 404 / NoSuchKey (on a conditional op) | `S3PreconditionFailedError` | caller | `3.1.1...flagged._.yield.md` topic 1 [FACT], src [1] |
| 409 / ConditionalRequestConflict | `S3ConditionalConflictError` (MalfunctionError) | retry | `3.1.1...flagged._.yield.md` topic 2 [FACT], src [2],[3] |
| every other status | rethrow raw | — | — |

### research traceability

each decision below cites the yield file AND its numbered source:

- **404-on-conditional-del → typed precondition error** — per `3.1.1...flagged._.yield.md`
  topic 1 [FACT] (src [1], AWS conditional-deletes userguide): "If the object doesn't exist when
  evaluating either of the preconditions, S3 rejects the request and returns a `Not Found` error."
  the vision's `[research]` flag on del-absent is thereby resolved; the build folds 404 into the
  same `S3PreconditionFailedError` so a caller catches one "my fenced write did not happen" error.
- **412 = stop, mapped to a ConstraintError (caller-must-fix)** — per topic 2 [FACT] (src [2],
  AWS conditional-writes userguide): "the write operation fails, resulting in a `412 Precondition
  Failed` response." this is a decided verdict, so it is a caller-fix constraint, not a retry.
- **409 = retry, mapped internally to a MalfunctionError** — per topic 2 [FACT] (src [2],[3]):
  "uploads may be retried after receiving a `409 Conflict` error." distinct from 412, so it must
  be modeled distinctly.
- **409 public shape — resolved posture (this wish)**: `S3ConditionalConflictError` IS exported now
  from both barrels, and this wish COMMITS to that as the shipped posture — 409 is a public typed
  error. this closes the vision's `[KHUE]` for the scope of this wish rather than leave it open in
  shipped code. resolution path for any FUTURE change: a later architect stone may narrow the posture
  (e.g. mark `S3ConditionalConflictError` `@internal` or rename it), which — because it is now public
  — would itself be a BREAKING change handled via the normal semver-major release flow. in short: the
  current answer is "export it"; a later reversal is an explicit, tracked semver-major break, not an
  ambiguous deferral. per topic 2 [FACT], 409 is always mapped to the typed class, never propagated
  raw.
- **`condition.etag: null → IfNoneMatch:'*'`; `etag → IfMatch`** — per `3.1.1...flagged._.yield.md`
  convergence signal (3+ sources [2],[4],[6],[7] agree on put-if-absent + compare-and-set
  semantics), realized by the `asS3ConditionHeaders` transformer.
- **[SUMP] / [OPIN] noted, not load-bearing** — the [SUMP] (conditional-delete announced
  2025-09-16, src [5]) explains why the vision saw "docs silent"; it shapes no code. the [OPIN]
  (412 = "lock held", 409 = "transient") informs the who-fixes column but is an opinion, cited as
  such.

### snapshots

acceptance snapshots are **deterministic** — this is a hard constraint (CI runs acceptance against
real s3 with no `--updateSnapshot`). therefore:

- KEYs may be uuids (isolation) but any value captured into `toMatchSnapshot` is a fixed literal or
  a masked token (prefix → `<prefix>/`, key → `<key>`).
- error messages are snapshotted **alongside** a `toBeInstanceOf` behavioral assertion, never alone.
- **etag quoted-format invariant asserted**: because the etag is an opaque fence token that must NOT
  be re-shaped (uc4), the meta tests assert the etag retains its s3-native surrounding double-quotes
  via `expect(etag).toMatch(/^".*"$/)` (or `expect.stringMatching(/^".*"$/)` in the snapshot matcher),
  alongside the `expect.any(String)` shape lock. this guards against a silent quote-strip that a bare
  `expect.any(String)` would let pass, and pins the round-trip-verbatim contract.

snapshot inventory:
- `index.acceptance.test.ts.snap` — set/get.one/del success + typed-error messages (masked). the
  precondition-error snapshots enumerate ALL conditional error-message variants so none is a blind
  spot: (a) 412 stale-etag-on-present, (b) 412 put-if-absent-on-present, (c) 404 conditional-del on
  absent, (d) 412 CAS-on-absent (case6). each masked message is snapped alongside its `toBeInstanceOf`
  check.
- `index.journey.acceptance.test.ts.snap` — get.all `{ key: '<prefix>/...', body }[]` (masked key)
- `throwMappedS3ConditionError.test.ts.snap` — deterministic message snapshots (fixed ref) for every
  mapped code: 412, 404-on-conditional, AND 409 → `S3ConditionalConflictError` (the 409 message IS
  snapped here from the synthetic exception, so the 409 error surface is captured deterministically
  even though the live 412/409 split is asserted by-set in `condition.concurrency.integration.test.ts`).

### test-coverage notes

- **`condition.integration.test.ts` ownership**: this file exercises the CROSS-op conditional-write
  matrix (matrix A/B/C) at the orchestrator grain — the (op × condition × object-state) rows that span
  `set` AND `del` together, plus the empirical del-absent probe (case5) and the CAS-on-absent probe
  (case6). it is COMPLEMENTARY to the per-op `set.integration.test.ts` / `del.integration.test.ts`
  (which cover each op's own happy/edge paths), not redundant: the matrix file owns the
  conditional-outcome cross-product, the per-op files own the per-op i/o.
- **fenced-release (compare-and-delete) narrative kept contiguous**: the fenced-release contract
  (Usecase 3) is expressed as ONE `given '[case3] fenced release (compare-and-delete)'` block with its
  positive and negative timesteps adjacent — `[t0]` compare-and-delete on a matched etag → succeeds,
  `[t1]` stale etag on present key → `S3PreconditionFailedError`, `[t2]` compare-and-delete on absent
  key → `S3PreconditionFailedError`. this replaces the earlier split across separate `case3`/`case5`
  blocks so the full fenced-release story reads top-to-bottom at one place instead of fragmented across
  two non-adjacent `given`s.
- **409 path coverage (committed at THREE layers — no deferral)**: rather than document the 409 path
  as a known gap, the plan commits deterministic coverage at every layer it CAN be reached, so no
  layer is deferred.
  - *layer 1 — mapper unit (deterministic)*: `throwMappedS3ConditionError.test.ts` feeds a synthetic
    `S3ServiceException` with `name: 'ConditionalRequestConflict'` and asserts it maps to
    `S3ConditionalConflictError`. this deterministically proves the s3-emits-409 → typed-error map with
    zero flake.
  - *layer 2 — type contract-lock at the barrel (deterministic)*: `index.acceptance.test.ts` asserts,
    on the class imported from the public barrel, `new S3ConditionalConflictError(...) instanceof
    S3ConditionalConflictError`, `... instanceof MalfunctionError`, and `error.code.exit === 1`. this
    proves the 409 type is a real, exported, `instanceof`-catchable type with the right exit semantics.
  - *layer 3 — live concurrency contract (deterministic assertion over real s3)*: a dedicated
    `condition.concurrency.integration.test.ts` fires N (≥ 16) concurrent put-if-absent writes to ONE
    fresh key against REAL s3 and asserts the deterministic outcome contract: exactly one write
    resolves, and EVERY loser rejects with an error that is `instanceof S3PreconditionFailedError` OR
    `instanceof S3ConditionalConflictError` (the typed precondition/conflict family). this reliably
    exercises the concurrent-conditional-write path end-to-end and reliably produces losers on every
    run; whether a given loser is a 412 or a 409 is set by s3's request ordering, but the ASSERTION is
    deterministic because both outcomes are enumerated as acceptable typed errors and any raw/untyped
    rejection fails the test. this converts the former "409 is not reproducible" deferral into a
    committed live test of the concurrency contract — the specific 412/409 split is s3's to decide, but
    the SDK's promise (every concurrent loser surfaces a typed conditional error, never a raw fault) is
    verified against real s3. the file carries the comment
    `// concurrency contract: exactly one put-if-absent wins; every loser is a typed`
    `// S3PreconditionFailedError|S3ConditionalConflictError. the 412-vs-409 split is s3-ordered, so we`
    `// assert the typed-error SET, not a fixed code — deterministic assertion over a live path.`
- **unconditional `del` on an absent key**: the idempotent no-op path (`del` without condition on a
  key that does not exist → resolves without error, s3 204) is covered by a dedicated case in
  `del.integration.test.ts` (given absent key / when del without condition / then resolves), and is
  also exercised by the crud journey cleanup steps.
- **404 disambiguation — conditional vs unconditional (structurally guarded)**: `throwMappedS3ConditionError`
  is invoked ONLY by the conditional-write communicators (`setS3Object`/`deleteS3Object`); `getS3Object`
  owns its own 404→null path and never calls the mapper. so an unconditional read's 404 can never
  reach the precondition map. to lock this against regression, `throwMappedS3ConditionError.test.ts`
  enumerates the 404 cases explicitly: 404 + `condition = null/absent` → rethrow raw (NOT a
  precondition error); 404 + `condition = { etag: null }` → `S3PreconditionFailedError`; 404 +
  `condition = { etag: '<etag>' }` → `S3PreconditionFailedError`. this pins uc6 (non-precondition
  faults not misreported).
- **`getAll` `content → body` structural guard**: beyond the semver-major release note, the `getAll`
  integration + acceptance tests assert `.content` is `undefined` on results (and `.body` is present),
  so a regression that re-introduces `content` is caught at test time, before release, not only by the
  commit-prefix convention.
- **subtle uc4/uc6 assertions locked at acceptance**: (a) `get.one` with `include.meta` on an ABSENT
  key asserts `expect(result).toBeNull()` explicitly (not merely a snapshot), pinning "null, not a
  hollow envelope"; (b) the etag round-trip (capture `meta.etag` from `get.one`, reuse verbatim as a
  later `condition.etag`) is exercised end-to-end in `index.mutex.journey.acceptance.test.ts` (t1
  acquire captures the token, t3 release reuses it); (c) the precondition-failed path asserts
  `expect(err.message).toContain(key)` alongside the `instanceof` + masked-message-snapshot, so a
  message regression (empty/wrong-key/no-recovery-hint) fails loud rather than pass silently.

## maintenance & readability notes

- **backwards compat** via `function` overloads on `set`/`getOne`: omit `condition`/`include` →
  today's `void` / `string | null` shape. no consumer change forced.
- **decode-friction eliminated**: header assembly and error-map live in named transformers, so the
  orchestrators read as narrative (per `rule.require.orchestrators-as-narrative`).
- **one new runtime dep**: `helpful-errors` (for `ConstraintError`/`MalfunctionError`), promoted
  devDep → runtime dep. all conditional i/o rides on the extant `@aws-sdk/client-s3` `IfMatch`/
  `IfNoneMatch` params.
- **the getAll rename** (`content → body`) is the single `[REPLACE]`; every other op already used
  `body`, so this aligns `getAll` with the canonical term.
- **release consequence of the getAll rename (semver-major)**: `get.all`'s return shape changes from
  `{ key; content }[]` to `{ key; body }[]` — a breaking change to a public contract. this MUST ship
  as a semver-major bump: the commit uses a `feat!:` header (or a `BREAKING CHANGE:` footer) so
  release-please issues a major bump, not a minor/patch. the `getAll` acceptance-snapshot update is an
  intentional breaking diff and should be called out as such in the PR. without this, a non-breaking
  commit prefix would silently ship a breaking change under a minor/patch version.
- **consumer migration guidance (required, not just an internal guard)**: the structural `.content`-is-
  `undefined` test guards the repo against regression, but does not tell a downstream consumer what to
  change. because this is a public SDK, the `BREAKING CHANGE:` footer MUST carry an explicit migration
  line so it lands in release-please's generated CHANGELOG: `BREAKING CHANGE: getAll now returns`
  `{ key, body } instead of { key, content }. migrate: rename result.content → result.body at every`
  `getAll call site.` TypeScript consumers get a compile error (the typed return no longer has
  `content`); loosely-typed / JS consumers would otherwise get a silent `undefined` at runtime, so the
  CHANGELOG line is their only signal — it is a required deliverable, not optional prose.
- **error-mechanism consistency — `asS3Ref` now throws a typed error (in scope)**: `asS3Ref` is a
  public-facing entry (re-exported paths flow through it on every op), so a plain `Error` on invalid/
  malformed uri would fall through every `instanceof`-typed catch a consumer writes — a divergent
  error contract on a public sdk. this blueprint COMMITS to `asS3Ref` throwing `BadRequestError` (a
  `helpful-errors` caller-must-fix class, exit 2), unifying the error surface with the conditional
  path's typed errors. the uri-error MESSAGES are preserved (e.g. still contain `invalid s3 uri
  scheme` / `malformed s3 uri`), so the journey acceptance assertions (`.rejects.toThrow('invalid
  s3 uri scheme')`, which match on message substring) continue to pass; only the thrown TYPE changes
  from `Error` to `BadRequestError`. this is a one-line-per-throw change, executed as part of this
  wish rather than deferred.
- **409 base class = `MalfunctionError` (considered vs `ConstraintError`)**: one interpretation holds 409
  should be a `ConstraintError` (caller-must-fix, exit 2) since the caller re-reads + retries. this
  blueprint retains `MalfunctionError` (exit 1, retry-may-help): a 409 is a TRANSIENT concurrency
  race, not bad caller input — the caller changes nothing and simply retries the SAME operation,
  which is the "retry may help" semantics `MalfunctionError` carries, distinct from 412's
  "caller-must-fix" `ConstraintError`. this keeps the 412-stop vs 409-retry split legible at the type
  level. the posture was research-flagged `[KHUE]` and is a defended judgment call, surfaced for
  scrutiny; the public export is committed (see contracts section) so any future change is a tracked
  semver-major.
- **`ContextSdkAwsS3` placement vs directional-deps (resolved)**: `ContextSdkAwsS3` references
  `S3Client` only as a TYPE annotation, so the import is erased at compile time and adds no runtime
  edge to `@aws-sdk/client-s3`. `rule.require.directional-deps` guards the value dependency graph;
  a type-only reference is not a structural dependency (no sdk value is instantiated, imported as a
  value, or bundled). it is therefore a genuine domain object and stays in `domain.objects/` beside
  `S3Ref` and the typed errors.
