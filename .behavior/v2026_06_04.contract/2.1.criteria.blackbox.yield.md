# blackbox criteria: sdk-aws-s3

## usecase.1 = get single object

### via URI

```
given an s3 object exists at 's3://bucket/path/to/object'
  when get.one is called with { uri: 's3://bucket/path/to/object' }
    then the object content is returned as a string
      sothat users can read objects with a single line of code

given an s3 object does not exist at 's3://bucket/path/to/absent'
  when get.one is called with { uri: 's3://bucket/path/to/absent' }
    then null is returned
      sothat users don't need try/catch for 404s

given an s3 bucket does not exist
  when get.one is called with { uri: 's3://nonexistent-bucket/key' }
    then an error is thrown with bucket context
      sothat users know the bucket is absent (not the object)
```

### via bucket+key

```
given an s3 object exists at bucket 'my-bucket' key 'path/to/object'
  when get.one is called with { bucket: 'my-bucket', key: 'path/to/object' }
    then the object content is returned as a string
      sothat users can use bucket+key when they don't have a URI

given an s3 object does not exist
  when get.one is called with { bucket: 'my-bucket', key: 'absent' }
    then null is returned
      sothat 404 semantics are consistent across input formats
```

## usecase.2 = get all objects with prefix

### via URI

```
given multiple s3 objects exist under prefix 's3://bucket/cache/'
  when get.all is called with { uri: 's3://bucket/cache/' }
    then an array of { key, content } is returned for each object
      sothat users can list and fetch in one call

given no s3 objects exist under prefix 's3://bucket/empty/'
  when get.all is called with { uri: 's3://bucket/empty/' }
    then an empty array is returned
      sothat users don't need special handle for empty results

given more than 1000 objects exist under a prefix
  when get.all is called
    then all objects are returned (pagination is handled internally)
      sothat users don't need to manage continuation tokens
```

### via bucket+prefix

```
given multiple s3 objects exist under prefix 'cache/' in bucket 'my-bucket'
  when get.all is called with { bucket: 'my-bucket', prefix: 'cache/' }
    then an array of { key, content } is returned for each object
      sothat users can use bucket+prefix when they don't have a URI
```

## usecase.3 = set object

### via URI

```
given an s3 bucket exists
  when set is called with { uri: 's3://bucket/new/object', body: 'content' }
    then the object is created with the given content
      sothat users can write objects with a single line

given an s3 object already exists at 's3://bucket/path/to/object'
  when set is called with { uri: 's3://bucket/path/to/object', body: 'new content' }
    then the object is overwritten with the new content
      sothat set is an upsert operation
```

### via bucket+key

```
given an s3 bucket exists
  when set is called with { bucket: 'my-bucket', key: 'path/to/object', body: 'content' }
    then the object is created with the given content
      sothat users can use bucket+key when they don't have a URI
```


### via bucket+key

## usecase.5 = URI parse

```
given a valid s3 URI 's3://my-bucket/path/to/key'
  when any operation is called with this URI
    then bucket is parsed as 'my-bucket'
    then key is parsed as 'path/to/key'
      sothat users can use familiar s3:// format

given an invalid URI 'http://example.com/path'
  when any operation is called with this URI
    then an error is thrown with clear message
      sothat users know the URI format is wrong

given a malformed URI 's3://'
  when any operation is called with this URI
    then an error is thrown with clear message
      sothat users get fast feedback on parse errors
```

## usecase.6 = context injection

```
given a custom S3Client is provided in context
  when any operation is called with { aws: { s3: { client } } } context
    then the custom client is used for the operation
      sothat users can inject test doubles or custom config

given no context is provided
  when any operation is called
    then a default S3Client is created
      sothat users don't need to manage client lifecycle for simple cases
```

---

## usecase.7 = error propagation

```
given an AccessDenied error occurs
  when any operation is called
    then the error is propagated with original context
      sothat permission issues are visible (not swallowed)

given a network error occurs
  when any operation is called
    then the error is propagated with original context
      sothat transient failures are visible

given a throttle error occurs
  when any operation is called
    then the error is propagated with original context
      sothat rate limit issues are visible
```
